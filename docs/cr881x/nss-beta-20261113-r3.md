# CR881x NSS beta r3: upgrading with existing settings

Factory reset is optional. The beta preserves compatible existing settings and
disables the two Linux firewall flow-offload options that conflict with NSS.
NSS/ECM itself remains enabled and starts automatically.

The packaged `99-qca-nss-qinq-firewall` default runs in boot S10, before
firewall S19. It commits both flags as `0` and is removed after success. Explicit
error checks keep it for retry if a set or commit fails, including when boot
sources it in a conditional subshell. It does not run as a persistent service.
Factory reset makes ROM defaults available again; the guard then runs once
again. Manually restoring a backup or enabling flow offload later can re-enable
the conflicting options: keep both off while using NSS.

## Real old-release migration test

The exact published `v26-ipq50xx-20260513-ax3000-cr881x` CR881x image was
downloaded, checksum-verified and booted on CR8812DX. It is kernel 6.12.87,
revision `r39559-2db347236c`, without NSS firmware/ECM acceleration packages.
Its `qca-nss-dp` package is the Ethernet datapath driver.

The clean old image did not generate `/etc/fw_env.config`: its setup script
looks for uppercase `0:APPSBLENV`, while this device exposes lowercase
`0:appsblenv`. For the existing-installation test, only the known-valid
boot-environment configuration was restored from the device backup. The old
LuCI, `/sbin/sysupgrade` and upgrade hook code were not patched or replaced.
This separate old-installation problem can prevent image validation before
the beta can run; the beta boot guard cannot fix a pre-flash rejection.

A test hostname, marker file and both offload flags set to `1` were recorded.
The actual old LuCI flash page uploaded the beta, validated it and invoked
`/sbin/sysupgrade -n /tmp/firmware.bin`. Keep settings was off. As expected
from the old cleanup bug, shared userdata remained intact. The beta booted
with the test hostname/marker retained, changed both offload flags to `0`,
consumed the guard and initialized eight QinQ nodes. No Linux flowtable was
active. No factory reset was performed for this acceptance.

| Routed TCP test, one direction at a time | Receiver rate | Sampled CPU idle |
| --- | --- | --- |
| LAN to WAN | 936.57 Mbps | 97.45% |
| WAN to LAN | 934.42 Mbps | 97.70% |

Both tests had active ECM flows, growing NSS firmware packet counters and no
additional NSS payload allocation failures. Dashboard, Devices, Wireless,
System, Backup/Flash Firmware, WAN Mode and QoS passed read-only browser checks.
Both AP radios initialized. Calibration/bdata hashes were unchanged. Only the
temporary test hostname and marker were removed afterwards.

## Optional reset

Users can retain settings that work. If clean defaults are wanted or retained
settings cause problems, use System → Backup/Flash Firmware → Reset to defaults
→ Perform reset, or run `factoryreset -y -r` after the beta boots. The r3
physical RESET handler uses the same built-in reboot for a 5–10 second hold and
release after boot. Its source/fixture tests passed; a physical-button hardware
test was not performed in this round. CLI reset was hardware-validated in r2.

After a reset, renew the computer's DHCP lease if needed and open
`http://192.168.2.1/` manually. LuCI may continue waiting for 192.168.1.1.

Arbitrary retained packages, custom VLAN/QoS combinations, AP-client load and
roaming/mesh are not comprehensively qualified by this migration test. The
previous simultaneous TCP asymmetry (~377 Mbps upload / 935 Mbps download) is a
known beta issue with unconfirmed cause; its investigation remains deferred.
Additional kmods require the exact matching kernel build; this beta does not
publish a separate matching module feed.
