# CR881x NSS beta, 2026-11-13

This build combines the current native Qosmio NSS/QinQ development branch with
Zcop as the default interface. Bootstrap remains installed as a fallback; Argon
is not selected. The build profile is `configs/xiaomi_cr881x_nss_qosmio.config`.
This is a beta image for testing, not a new hardware-qualification claim.

## Selected components

- Linux6.18.60, NSS firmware12.2 and the pinned Qosmio feed
  `0d970dbf0185e3f53709bd803e8a466598023c57`, with this tree's NSS overlay.
- Native automatic NSS startup, YT9215S QinQ DSA port identity, routed IPv4/IPv6
  and single-session PPPoE support, including the device-lifetime correction.
- The NSS package disables firewall4 software/hardware flow offloading on first
  boot and after factory reset, leaving NSS/ECM acceleration enabled. A parallel
  nft flowtable prevented forwarded TCP setup in the original beta's factory
  configuration. The same fixture passes936.6/931.9Mbps with those two options
  off, approximately97% CPU idle and no additional NSS payload allocation failures.
  This default is packaged with `qca-nss-qinq`; standard DSA builds keep their
  existing firewall defaults.
- LOW NSS allocation and the256MiB ath11k/NSS memory profiles, small host buffers
  and the existing512KiB coherent DMA pools. The memory reservation map is not
  enlarged for this image.
- Zcop theme0.1.14-r1 and Overview app0.8.2-r1: Dashboard, passive Devices,
  explicit Wireless scans, device names/static-lease staging, browser-side MAC
  vendor lookup and current-role port labels linked to WAN Mode.
- WAN Mode1.1.0-r1 and YT921x QoS1.1.0-r1, with their compact control layouts.

## Test scope

Previous test images established native routed NSS, selected DSA/VLAN/control
paths, DHCP WAN and laboratory PPPoE authentication/IPv6 prefix handling. See the
[NSS feature table](nss-feature-matrix.md), [PPPoE evidence](nss-pppoe.md),
[daily delivery checks](nss-qinq-daily-traffic.md) and [Wi-Fi results](nss-qosmio-wifi.md).
The app unit/browser checks and the focused lifecycle/QinQ/PPPoE source checks
pass before this beta build. A successful package/image build is separate from
boot and traffic validation of the newly produced image.

Wi-Fi AP use, roaming/mesh, combined Wi-Fi/VLAN configurations and some advanced
queue scheduling remain outside the completed device acceptance. Prior STA
measurements depend on their radio/peer fixture and are not a promise of a
particular Wi-Fi rate. PAP/CHAP tests use a controlled peer, not ISP credentials.

The output is a native-NSS CR881x sysupgrade image, with a checksum, resolved
feed list and build/configuration manifest retained beside the beta artifact.
Building this image does not flash a device or publish a GitHub release.

## Factory-reset acceptance and correction

The original beta boots on CR8812DX with eight QinQ nodes, both256MiB Wi-Fi
profiles, two initialized AP radios and working Dashboard/Devices/Wireless/
System/WAN Mode/QoS pages. Its clean factory configuration enabled both Linux
flow-offload options, unlike the prior working saved configuration. This breaks
the forwarded iperf control exchange before NSS rule creation. Disabling both
restores routed throughput and ECM/firmware counter growth; NSS itself stays on.

The original beta's upgrade hook did not clear the separate shared userdata
overlay with `sysupgrade -n`. The corrected hook now prepares a next-boot reset
from RAMFS, restoring only the selected backup when keep-settings is requested.
See [shared userdata upgrade handling](upgrade-reset.md). Its production-script
fixtures cover both slots, keep/reset and failure paths. For a manual reset,
use `factoryreset -y -r` so sync/reboot does not launch from a deleted overlay.

The r2 image was built from `00e457b50d6abf410935bda781970bda02bff58c` and
flashed to CR8812DX slot0 using `sysupgrade -n`. The old running image's hook
was temporarily bound to the exact corrected source before this first
transition. UART recorded shared userdata preparation and the next-boot
overlay reset. The test marker and changed hostname disappeared, the default
hostname and Zcop theme returned, both flow-offload flags were already 0, and
eight QinQ nodes initialized without manual configuration correction.

A second test changed the hostname and planted another marker, then ran
`factoryreset -y -r`. It rebooted without a power cycle, removed both test
markers and again applied the same defaults. Both resets were followed by
forwarded TCP tests with active ECM flows and NSS firmware packet growth:

| Reset path | LAN to WAN | WAN to LAN | Sampled CPU idle |
| --- | --- | --- | --- |
| `sysupgrade -n` to r2 | 936.61 Mbps | 936.62 Mbps | 95.50 / 96.84% |
| r2 `factoryreset -y -r` | 935.79 Mbps | 936.64 Mbps | 95.76 / 96.24% |

No NSS payload allocation failures accumulated in these runs. Dashboard,
Devices, Wireless, System, WAN Mode and QoS passed read-only browser checks
after both resets. The fallback slot1 image and factory calibration/bdata
partition hashes stayed unchanged. The running system remains at factory
defaults; Wi-Fi AP startup is checked, not client throughput or roaming.
Keep-settings upgrades and Redmi AX3000 are covered by the offline harness,
not by this CR8812DX reset acceptance.

The retained r2 sysupgrade image is 18,585,888 bytes, SHA256
`e387ecb7f2b9c60a4716686c3a501c1ebdb3f5ad19b6902e4f6cee617db87d6e`.
Build inputs, UART capture, reset evidence, traffic JSON, UI screenshots and
private recovery copies are under the ignored local directory
`logs/cr881x-nss-beta-r2-20261113/`. No GitHub release was created.

A separate nonfatal startup warning remains: the upstream NSS IRQ script tries
to pin the PPDU interrupt to CPU2 on a two-CPU board. The write is rejected, the
interrupt retains CPUs0-1, NSS queues stay on CPU0/CPU1 and NSS RPS stays enabled.
The reported routed throughput already includes this condition. This change
does not alter that independent affinity policy.
